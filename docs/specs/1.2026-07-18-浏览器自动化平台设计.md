## 1. 项目概述

### 1.1 定位

Browser Auto Hub 是一个**浏览器自动化任务管理平台**，提供：
- Pipeline 注册与管理（高码开发，代码级自动发现）
- 定时/API/手动 三种触发方式
- 实时执行监控（步骤日志 + SSE 推送）
- Pipeline 业务文件存储（MinIO，仅 pipeline 侧使用）
- Docker 一键部署

### 1.2 核心场景

- 数据采集：从目标网站自动采集结构化数据
- 表单填写：模拟人工操作填写在线表单
- 浏览器自动化：点击、导航、翻页等自动化操作
- 任务编排：多步骤 Pipeline 顺序执行

### 1.3 非目标（POC 阶段不做）

- Pipeline 上传/下载（高码模式无需）
- 用户权限管理/多租户
- 分布式 worker 扩展
- 低代码/拖拉拽 Pipeline 编辑器

## 4. Pipeline 注册机制

### 4.1 设计原则

- **代码即配置**：Pipeline 通过 Python 装饰器声明元数据
- **启动时自动发现**：backend 启动时扫描 `engine/pipelines/` 目录
- **数据库同步**：发现的 Pipeline 元数据同步到 MySQL（用于前端查询和调度关联）

> 2026-07-22 十三次修订：明确同步生命周期（对齐 Airflow `deactivate_deleted_dags` 业界惯例）——
> 代码是「定义」唯一真相，DB 是「运维状态 + 外键锚点」。详见 §4.5。

### 4.5 版本声明与同步生命周期（十三次修订新增）

> 2026-07-24 二十七次修订：sync 触发条件由「version 变化」改为**内容对比**——
> display_name / description / trigger_modes / config_schema / version 任一与
> registry 不一致即覆盖全部定义字段。实证动因：新增 config_schema 键但忘 bump
> version → DB schema 不更新 → 前端表单不显示新字段（oa.communicate_todos
> max_verify_rounds 事件）。version 自此**不再承担变更检测职责**，纯作溯源标记
> （pipelines.version + task_executions.pipeline_version）；开发者无需再为
> 「改 schema 必须 bump version」纪律负责。

**版本声明**：`PipelineMetadata` 增加 `version: str`（开发者自定义，建议 semver，装饰器缺省 `"1.0.0"`）。
版本是纯观测/溯源标记，不做依赖解析、不做执行 pin（新执行永远跑最新代码——短任务惯例）、
不做同步触发（二十七次修订起由内容对比取代）。

**启动 sync 语义**（`pipeline_sync.py`）：

```
对 registry 中每个 pipeline:
  ├── DB 不存在 → 插入（含 version）
  ├── DB 存在且任一定义字段不同 → 更新定义字段(display_name/description/trigger_modes/config_schema) + version
  │   （二十七次修订：逐字段内容对比，version 差异只是差异之一，不再是唯一触发）
  ├── 定义字段全部一致 → 跳过
  └── DB status = archived → 恢复为 active（代码回归，系统标记复位）
对 DB 中 registry 找不到的 pipeline（代码已删除）:
  └── status → archived —— 软归档，绝不删行
```

- **archived 语义**：列表默认隐藏；触发返回 400；调度器跳过；历史执行/调度外键完好。
  复用现有 `status != "active"` 全部防线，不新增机制。
- **执行版本快照**：`task_executions.pipeline_version` 在创建执行记录时写入当时
  `pipelines.version`，历史执行可溯「当时跑的是哪版」；前端执行详情展示版本。
- **已知边界**（单枚举代价）：用户手动 disabled → 代码删除(archived) → 代码恢复 →
  回 active，停用意图丢失，需手动再停。接受此取舍。

### 4.2 Pipeline 基类

```python
from abc import ABC, abstractmethod
from dataclasses import dataclass
from typing import Literal

@dataclass
class PipelineMetadata:
    name: str                          # 唯一标识符
    display_name: str                  # 前端显示名
    description: str                   # 描述
    trigger_modes: list[Literal["cron", "interval", "api", "manual"]]
    config_schema: dict | None = None  # JSON Schema，描述可配置参数
    version: str = "1.0.0"             # 开发者自定义版本（十三次修订新增）

class BasePipeline(ABC):
    metadata: PipelineMetadata

    @abstractmethod
    async def execute(self, config: dict, logger: StepLogger) -> PipelineResult:
        """执行 Pipeline，通过 logger 记录步骤日志"""
        ...
```

### 4.3 注册装饰器

```python
def register_pipeline(**kwargs):
    """装饰器：注册 Pipeline 到全局 registry"""
    def decorator(cls):
        cls.metadata = PipelineMetadata(**kwargs)
        PipelineRegistry.register(cls)
        return cls
    return decorator
```

### 4.4 示例 Pipeline

```python
@register_pipeline(
    name="oa_communicate_todos",
    display_name="OA 沟通待办采集",
    description="采集 OA 系统沟通待办列表及详情，产出 JSONL 文件",
    trigger_modes=["cron", "api", "manual"],
    config_schema={
        "type": "object",
        "properties": {
            "username": {"type": "string"},
            "password": {"type": "string"},
            "concurrency": {"type": "integer", "default": 1, "minimum": 1, "maximum": 10},
        },
        "required": ["username", "password"]
    }
)
class OaCommunicateTodosPipeline(BasePipeline):
    async def execute(self, config: dict, logger: StepLogger) -> PipelineResult:
        logger.step("login", "登录 OA 系统")
        # ... 执行逻辑
        logger.step("extract", "提取待办列表")
        # ...
        return PipelineResult(success=True)
```

## 5. 数据库模型

### 5.1 ER 关系

```
pipelines 1──N schedules 1──N task_executions 1──N task_logs
```

> 十七次修订（2026-07-23）：库表精简。删除 `task_artifacts` 整表（零写入方的死表）、`task_logs.screenshot_key` 与 `task_logs.metadata` 死列、`schedules.next_run_at` 死列（从未写入，API 实时计算）；截图链路整体退役（§9.3）；MinIO 配置收归 .env 唯一来源，不再入 system_settings。平台层表不再有任何 MinIO 引用——MinIO 仅为 pipeline 业务运行时设施（如 OA 附件）。
>
> 十八次修订（2026-07-23）：基础设施只连不建。库表与 MinIO bucket 一律由部署方提前创建，应用启动不再执行 `create_all`/列迁移/`ensure_bucket`——连接失败即启动报错，不做任何 DDL。Settings 删除零消费方的 `app_secret_key`/`app_log_level`；`.env` 精简为 `DATABASE_URL` + `MINIO_*` 六项 + `BACKEND_PORT`/`FRONTEND_PORT`（compose 端口可选覆盖，缺省 8900/3200）；docker-compose 移除 mysql/minio 自建服务及 `config/` 空挂载（部署拓扑 = backend + frontend 两服务，外部连接已 provisioning 的 MySQL/MinIO）。

> 十九次修订（2026-07-23）：脚手架 `example` pipeline 彻底移除——代码文件删除，DB 中其 pipelines 行及关联 task_logs/task_executions 一并清除（非常规归档，属一次性清理；软归档规则仅约束代码删除时的自动行为）。
>
> 二十次修订（2026-07-24）：pipelines 表删除 `max_concurrent` / `timeout_seconds` 两列，并发上限与单次执行超时功能整体退役——定位调整：pipeline 属性只保留与自身业务密切相关的定义字段，运维约束不设 per-pipeline 旋钮（低并发内部工具场景，过度设计）。runner 不再做并发闸门（execution 派发即运行）与 `asyncio.wait_for` 超时强杀；`PATCH /api/pipelines/:name` 仅保留 `status`（启停）。存量库执行 `ALTER TABLE pipelines DROP COLUMN max_concurrent, DROP COLUMN timeout_seconds`（列迁移属部署方 DDL，对齐十八次修订"只连不建"）。
>
> 二十七次修订（2026-07-30）：**产出表归属约定（账本 vs 当前态双维度）**。pipeline 私有产出表（首例：`ganghang_materials`）采用 SCD1 覆盖式更新（URL 唯一、原地 UPDATE 保最新值），并引入两列：`execution_id VARCHAR(36) NULL`（最后写入者——INSERT 与内容覆盖 UPDATE 时原子刷新，force 覆盖下自维护）与 `updated_at DATETIME ON UPDATE CURRENT_TIMESTAMP`（最后写入时间，MySQL 自动维护；`updated_at > created_at` 即"被覆盖过"）。语义分工必须严格区分：**账本维度**（task_executions/task_logs/result_summary）记录"执行当时做了什么"，append-only 永真；**当前态维度**（产出表）只回答"这行现在是什么/归谁写"。因此按执行对账的权威入口是 `result_summary.outcomes`（逐条 title/url/decision/db_id/is_new，含已删除行），`WHERE execution_id = X` 只表示"当前仍归属 X 的行"（被后续执行覆盖的行会改嫁，属特性非 bug）。不采用 SCD2/历史版本表——月刊选稿只消费最新值，历史查询走账本维度。
>
> 二十八次修订（2026-07-30）：**相对日期表达式（滚动周期）**。日期型 config 字段除 `YYYY-MM-DD` 外允许 `today` / `today-N` 表达式，由 pipeline 在**每次执行时刻**解析为本地日期（cron 定时任务因此获得滚动窗口，如 start=today-6,end=today 恒为近7天）；execution.config 保留表达式原样（调度意图可溯），解析结果入 `result_summary.period`。解析下放 engine pipeline 本地（单一消费方，不做平台级模板引擎）。前端 SchemaFields 新增 schema 标记 `x-range-group`/`x-range-part`/`x-allow-relative`：成对日期字段合并渲染为周期复合控件（固定日期 RangePicker+快捷预设 / 相对周期预设 Select 两模式），存储仍写两个扁平 key，渲染器保持 schema 驱动（spec 4 §4.4）。
>
> 二十九次修订（2026-07-30）：**config 边界预校验（validate_config 钩子）**。`BasePipeline` 新增可选类方法 `validate_config(config) -> str | None`（返回错误信息，None 通过，默认放行）；backend 在 `POST /api/executions`、`POST/PUT /api/schedules` 落库/派发前调用，失败同步返回 422——非法入参从「201 → 异步 failed 记录」改为即时拒绝，执行记录表只留真实执行过的任务。校验逻辑由 pipeline 自实现（语法单一事实源在 engine，backend 只做调用方，不做平台级通用 jsonschema 校验）；`execute` 内校验保留为最后防线（防御纵深）。首例：port_maritime_info.harvest 校验 sources 必填 + 日期 union 语法（YYYY-MM-DD | today | today-N，解析后 start<=end，非字符串类型混淆归一为格式错误）。
>
> 三十次修订（2026-07-30）：**result_summary.outcomes 收窄为留存清单**（修订二十七次修订的"含已删除行"约定）。`GET /api/executions/{id}` 的 `result_summary.outcomes` 只收录运行后仍存在于产出表的行（`pass`=本次写入/更新，`kept`=force 模式保留的历史行），回答"本次运行留存了哪些"；reject/failed 行已物理删除，不再落 result_summary。全量逐条决策（含拒绝理由/失败原因）的权威入口改为执行日志「阶段归纳」（`_recap` 仍按 pass/reject/kept/failed 四组全量输出，账本维度改由 task_logs 承载）。二十七次修订的其余约定（SCD1、execution_id/updated_at 双维度）不变。

## 6. API 接口设计

**寻址约定（二十二次修订明确）**：pipeline 以 `name` 为自然键寻址（代码注册资源、全局唯一、
人类可读，同 GitHub `/repos/{owner}/{repo}` 惯例）；schedules / executions 为运行期数据行，
以 UUID `id` 寻址。pipeline 的公开标识一律为 name——`POST /api/executions` 的 `pipeline`
字段、`GET/PATCH /api/pipelines/:name` 均用 name；schedules 行内 `pipeline_id` 仅为内部外键。

### 6.1 Pipeline 管理

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | /api/pipelines | 获取所有已注册 pipeline 列表 |
| GET | /api/pipelines/:name | 获取单个 pipeline 详情 |
| PATCH | /api/pipelines/:name | 启停（请求体 `{"status": "active" \| "disabled"}`，二十次修订起仅此字段） |

### 6.2 调度管理

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | /api/schedules | 获取所有调度配置（支持 `?pipeline_id=` 过滤） |
| GET | /api/schedules/:id | 单个调度详情 |
| POST | /api/schedules | 创建调度配置（201） |
| PUT | /api/schedules/:id | 修改调度配置（部分字段更新，exclude_unset 语义） |
| PATCH | /api/schedules/:id | 启用/禁用（请求体 `{"enabled": bool}`，显式目标态、幂等） |
| DELETE | /api/schedules/:id | 删除调度配置（204） |

### 6.3 任务执行

| 方法 | 路径 | 说明 |

## 10. playwright-cli 集成方案

playwright-cli 是 Node.js CLI 工具，在 Python engine 中通过 subprocess 调用：

```python
class PlaywrightCliExecutor:
    """通过 subprocess 调用 playwright-cli 命令"""

    async def run_command(self, command: str, args: list[str]) -> str:
        proc = await asyncio.create_subprocess_exec(
            "playwright-cli", command, *args,
            stdout=asyncio.subprocess.PIPE,
            stderr=asyncio.subprocess.PIPE,
        )
        stdout, stderr = await proc.communicate()
        if proc.returncode != 0:
            raise PlaywrightCliError(stderr.decode())
        return stdout.decode()

    async def open_page(self, url: str, session: str = "default") -> None:
        await self.run_command("goto", [url, f"--session={session}"])

    async def snapshot(self, session: str = "default") -> str:
        return await self.run_command("snapshot", [f"--session={session}"])

    async def click(self, ref: str, session: str = "default") -> None:
        await self.run_command("click", [ref, f"--session={session}"])
```

Docker 镜像中需同时安装 Node.js 和 playwright-cli：
```dockerfile
# 在 Dockerfile.backend 中额外安装
RUN apt-get install -y nodejs npm && npm install -g @playwright/cli
```

Pipeline 可选择使用 browser-use（纯 Python）或 playwright-cli（通过 subprocess），根据具体任务需求选择执行器。

## 14. 时间与时区规范（十六次修订新增）

全平台时间处理遵循业界标准：**UTC 存储 + 时区后缀传输 + 显示边缘转换**。MySQL `DATETIME` 为 naive 类型（不记录时区），统一存 UTC 是唯一与环境零耦合的选择；裸 SQL 查询看到的值与本地墙钟差 8 小时（UTC+8）是正确实现的固有外观，不是 bug。

| 维度 | 规范 | 实现 |
|------|------|------|
| 数据库存储 | 一律 UTC；默认值用 UTC 时钟 | 所有时间列用 `UTCDateTime` 类型 + `func.utc_timestamp()` server_default；`test_utc_datetime.py` 守门 |
| 服务器/引擎代码 | 全程 tz-aware UTC，禁止 naive `datetime.now()` | `datetime.now(timezone.utc)`（runner / step_logger / engine logger / forward 回写） |
| ORM 读写 | 写入剥 tz（存 naive UTC）；读回补 `tzinfo=UTC` | `UTCDateTime.process_bind_param / process_result_value` |
| API 传输 | ISO 8601 必须带时区后缀（`Z` 或 `+00:00`），绝不传裸时间字符串 | pydantic 自动序列化；手工 `isoformat()` 处必须 tz-aware |
| 前端显示 | 仅在显示边缘转换一次，用浏览器本地时区 | `new Date("...Z").toLocaleString("zh-CN")` |
| 用户输入 | 边界接收带时区值 → 先转 UTC 再剥 tz 存储 | 前端 `dayjs.toISOString()`；后端 `_to_utc_naive()` |
| 调度语义 | cron 表达式 = 本地墙钟（用户预期）；单次/下次执行时刻 = UTC 存储、tz-aware 计算 | `CronTrigger`（本地时区）+ `DateTrigger(astimezone())` |
| 业务日统计 | **按用户本地日切割**，不用 UTC 日 | "今日"统计取本地零点转 UTC-naive 后与存储比对 |
| 源数据时间 | 外部系统抓取的时间字符串原样保留，不做转换 | 如 `inbox_documents.send_time`（OA 北京时间字符串） |
| 裸 SQL 排查 | 查询时用 `CONVERT_TZ(col, '+00:00', '+08:00')` 转视角，不改存储 | — |

反面清单（禁止出现）：
- `func.now()` / `NOW()` 作为列默认值（服务器本地时区，容器时钟不可靠）
- naive `datetime.now()` 写入时间列
- API 返回无时区后缀的时间字符串
- 带时区的值未转 UTC 直接 `replace(tzinfo=None)` 存储
