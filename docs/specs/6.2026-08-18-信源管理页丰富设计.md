# 信源管理页丰富设计

> 日期：2026-08-18
> 状态：待实施
> 依赖：spec 1（平台架构）、spec 4（前端重设计 §2.1/§2.6/§2.7）、spec 3（port_maritime_info pipeline）

---

## 1. 背景与目标

spec 4 §2.7 已定义信源管理页（`/sources`）为只读展示页，从 `engine/pipelines/port_maritime_info/sources.json`
读取 4 信源 20 entry，用 §2.6 统一列表页骨架（FilterBar + 表格 + 展开行）展示。上一轮基础版已落地
（3 列主表 + 2 列展开子表，侧边栏位于「执行记录」后）。

本轮目标：**丰富表格展示**，把 sources.json 里更多结构信息（采集字段、详情变体、自定义 entry、
分页配置）以列形式呈现，让信源管理页成为完整的"采集源结构参考"视图。同时调整侧边栏位置
使信源管理与配置类页面（流水线）归类。

**明确不做**：per-source 采集状态/执行结果联动——经充分论证，历史执行记录未单独记录 per-source
状态（task_executions 是整批维度），且不新增表/不改 pipeline。该能力本轮放弃，详见 §6 已否决方案。

## 2. 影响范围（关键确认）

| 层 | 改动 | 现有功能/库表 |
|---|---|---|
| DB schema | 无 | 零影响——无新表、无新列、无迁移 |
| pipeline (harvest.py) | 无 | 零影响——不碰采集逻辑 |
| 现有 API（executions/schedules/pipelines/system） | 无 | 零影响 |
| `GET /api/sources`（已建只读端点） | `SourceOut` 追加字段，全部从 sources.json 结构派生 | 向后兼容——只增不改不删 |
| 前端 `Sources.tsx` | 列 3→7，加表标题"采集源网站" | 仅本页展示 |
| 前端 `MainLayout.tsx` | menuItems 重排（信源管理移到调度管理前） | 仅菜单顺序 |
| 前端 `types/index.ts` | Source/SourceEntry 接口加字段 | 类型扩展 |
| spec 4 §2.1/§2.7 | 文档更新 | 文档 |

纯展示层优化 + 一个只读端点响应字段扩展。不碰 DB、不碰 pipeline、不碰现有功能行为。

## 3. 侧边栏位置调整（spec 4 §2.1）

```
看板 → 流水线 → 信源管理 → 调度管理 → 执行记录 → 系统设置
                    ↑ 从原（执行记录后）移到调度管理前
```

**理由**：信源是静态配置/参考视图，与流水线（配置类）归类，先于运维视图（调度/执行）。
侧边栏仍 6 项，数量不变，仅 `信源管理` 的位置在 menuItems 数组中从 index 4 移到 index 2
（流水线之后、调度管理之前）。

## 5. 主表列（6 列）

| 列 | 来源字段 | 宽 | 渲染 |
|---|---|---|---|
| 信源名称 | `source_name` | 140 | 文本 |
| 网站地址 | `base_url` | flex | ellipsis + `<a href target=_blank rel=noopener>` |
| 采集入口数量 | `entry_count` | 120 center | 数字（3 / 2 / 10 / 5 — 有区分度） |
| 详情变体 | `detail_variant_count` | 90 center | 数字 + tooltip "详情页模板变体数"（2 / 1 / 1 / 3 — 有区分度） |
| 列表字段 | `list_fields` | 220 | Tags: `container`·`item`·`title`·`date`·`link`（统一 5 项，结构参考） |
| 详情字段 | `detail_fields` | 200 | Tags: `content`·`title`·`date`·`source`（统一 4 项，结构参考） |

- `expandRowByClick: true`，`defaultExpandAllRows: true`（页面加载即全部展开，点击行可折叠），`rowKey="source_name"`，`scroll={{ y: fill.scrollY }}`
- `pagination={{ ...TABLE_PAGINATION }}`（前端分页，4 条数据）
- 不设 `scroll.x`——弹性列（网站地址）吸收剩余宽度，无横向滚动

**列设计原则**：有区分度的字段（入口数/详情变体）作主信息列；统一字段
（列表/详情字段名）作 Tags 结构参考列——即使值相同，Tags 让"采集结构是什么"一目了然，
符合用户"采集字段虽每个源都一样但也可以体现"的诉求。

> 自定义入口列（`entries_with_override`/`entry_count`）已移除：标题与取值在窄列下
> 易换行，且信息可由展开子表的「采集规则」列体现（标「自定义」的入口即覆盖默认规则）。
> 后端 `entries_with_override` 字段保留（1 行派生、已测试、零成本）。
> 分页列同理已移除（4 信源统一 ✓，零区分度）。

## 6. 可展开行（入口子表，3 列）

点击行展开内嵌子表，`size="small"` `pagination={false}`，**不加 `fill-table` class**
（避免与主表 min-height CSS 冲突，沿用 spec 4 §2.7 既有约定）：

| 列 | 来源 | 宽 | 渲染 |
|---|---|---|---|
| 采集入口 | `entry_name` | 200 | 文本 |
| 网址 | `url` | flex | ellipsis + `<a href target=_blank>` |
| 采集规则 | `has_override` | 100 center | `自定义`（橙 Tag）/ `标准`（绿 Tag） |

- 工信部的 4 个新闻发布会入口标「自定义」（它们有自定义 date 选择器 `span.list-time`），
  其余标「标准」——一眼看出哪些入口用了非标列表模板（自定义=该入口覆盖了信源默认列表选择器，标准=沿用默认）。
- `rowKey="url"`，网址列用 `<a target="_blank">` 可跳转

## 7. 后端 `SourceOut` 扩展

`packages/backend/src/backend/api/sources.py` 的 `list_sources` 端点扩展响应模型：

```python
class SourceEntryOut(BaseModel):
    entry_name: str
    url: str
    has_override: bool            # 该 entry 是否有 list override（entries[i].list 存在）

class SourceOut(BaseModel):
    source_name: str
    base_url: str
    entry_count: int
    entries: list[SourceEntryOut]
    list_fields: list[str]            # configs.list.fields 的 key 集合
    detail_fields: list[str]         # configs.detail[0].fields 的 key 集合
    detail_variant_count: int        # len(configs.detail)
    has_pagination: bool             # configs.pagination 存在
    entries_with_override: int       # COUNT(entries[i].list 存在)
```

`list_sources` 实现从同一份 sources.json 派生上述字段：

```python
for s in data.get("sources", []):
    cfg = s.get("configs", {})
    list_fields = list(cfg.get("list", {}).get("fields", {}).keys())
    detail_cfgs = cfg.get("detail", [])
    detail_fields = list(detail_cfgs[0].get("fields", {}).keys()) if detail_cfgs else []
    entries_raw = s.get("entries", [])
    entries_with_override = sum(1 for e in entries_raw if e.get("list"))
    result.append(SourceOut(
        source_name=s["source_name"],
        base_url=s["base_url"],
        entry_count=len(entries_raw),
        entries=[SourceEntryOut(
            entry_name=e["entry_name"], url=e["url"],
            has_override=bool(e.get("list")),
        ) for e in entries_raw],
        list_fields=list_fields,
        detail_fields=detail_fields,
        detail_variant_count=len(detail_cfgs),
        has_pagination=bool(cfg.get("pagination")),
        entries_with_override=entries_with_override,
    ))
```

**不暴露 CSS 选择器值**（container/item 等的选择器字符串），仅返回字段**名**与**结构计数**——
延续 spec 4 §2.7"不暴露 configs（CSS 选择器等采集规则）"语义，仅暴露结构供展示。

## 10. 已否决方案（per-source 采集状态联动）——记录备查

本轮曾深入论证"信源管理页显示每信源最新采集状态（成功/失败/无新增）+ 点击跳执行记录"，
经三轮方案对比后否决：

- **方案 A 新建 `source_runs` 表**（Airflow task_instance 模式）：架构正确但 schema 改动大，用户否决
- **方案 B `result_summary.sources` JSON 内嵌**：不可 SQL 查询、违反项目关系型风格
- **方案 C 纯派生**（materials + execution 状态代理）：状态不精确，不满足"单独记录"语义
- **方案 task_logs 复用**（step_name=source_name + level 映射状态）：架构最佳，但历史执行
  当时未 emit per-source log，**历史 per-source 状态不可恢复**——只有未来执行能精确。用户
  因"历史数据无法体现"放弃整个功能。

核心数据事实（备忘）：`task_executions` 是整批维度（status/result_summary 聚合，config.sources
数组仅记录覆盖范围），`task_logs` 历史 step_name 是阶段名（summary/dedup/粗筛）非信源名，
`ganghang_materials` 有 `website_name`+`execution_id` 可派生 per-source 条目数但派生不出状态。
若未来重启该功能，方案：harvest.py per-source try/except + `log.info/error(source_name, JSON payload)`
写入 task_logs，后端 `WHERE step_name=:source ORDER BY timestamp DESC LIMIT 1` 查最新——
纯复用现有表，零 schema 改动。
