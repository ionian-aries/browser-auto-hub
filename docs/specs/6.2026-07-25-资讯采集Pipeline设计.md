# 资讯采集 Pipeline 设计

> 序号：6 | 创建日期：2026-07-25
> 对齐：场景二《港航信息》编撰 — 资讯 8 类采集入库全流程

---

## 一、定位与范围

### 1.1 业务定位

本 Pipeline 替换来也 RPA 的资讯采集服务，承担从「网页采集 → LLM 粗筛/细筛 → 入库」的全链路。自成服务，通过平台已有的 cron / api / manual 三种触发模式运行，并提供 HTTP 查询接口供下游 Skill 消费。

### 1.2 范围

| 范围 | 说明 |
|------|------|
| **本次实现** | 资讯 8 类采集、粗筛、细筛、入库全流程 |
| **后续扩展** | 固定 5 类（港口吞吐量等周期性数据） |
| **不含** | 成稿编撰 Skill、钉钉推送、人机协同修改 |

### 1.3 核心设计原则

| 原则 | 说明 |
|------|------|
| **Config 优先，LLM 兜底** | 采集/翻页/正文提取都优先用预存 config（CSS 选择器或 JS 代码块），失败时降级到探索 Agent |
| **探索结果持久化** | 探索 Agent 产出的 config 写入 DB，下次直接用，不重复探索 |
| **粗筛批量、细筛逐篇** | 粗筛按 20 条/批调 LLM 降成本，细筛逐篇打分保证精度 |
| **单次执行端到端** | 从信源遍历到入库，一次 pipeline 执行完成全流程 |
| **温和爬取** | 限速、退避、每日配额，避免被目标站判定为网络攻击 |

## 二、架构方案

### 2.1 方案选择：单 Pipeline + 顺序阶段（方案 A）

```
execute()
  ├── Phase 1: 信源遍历 & Config 解析
  ├── Phase 2: 翻页采集
  ├── Phase 3: URL 去重
  ├── Phase 4: 粗筛（LLM 批量）
  ├── Phase 5: 正文提取
  ├── Phase 6: 细筛（LLM 逐篇）
  └── Phase 7: 入库 + 统计报告
```

选择理由：
1. 与现有 OA pipeline 的 `@register_pipeline` + `execute()` 模式一致
2. 顺序阶段最容易端到端验证
3. 模块拆分为独立文件，pipeline 类只做编排调度
4. 并发在需要时通过 `asyncio.Semaphore` 控制

### 2.2 数据流总览

```
用户触发(manual/cron/api)
  │
  ▼
加载执行配置（信源URLs + 日期范围 + 查询偏好）
  │
  ▼
┌─ 遍历每个信源的每个 entry ────────────────────────────┐
│                                                        │
│  有config? ──是──→ config执行采集 ──成功?──是──→ 翻页采集 │
│     │                    │                            │
│     否                 否                             │
│     │                    │                            │
│  探索Agent ──→ 生成config  修复config ──┘              │
│                                                        │
└────────────────────────────────────────────────────────┘
  │
  ▼
URL去重（内部 + 查DB）
  │
  ▼
粗筛 - LLM批量（20条/批，news-coarse prompt）
  │
  ▼
正文提取（config优先 → 失败降级探索Agent）
  │
  ▼
细筛 - LLM逐篇（news-fine prompt，GATE→CLASSIFY→GENERATE→SCORE）
  │
  ▼
入库（decision=pass + score≥6.0 → INSERT documents）
  │
  ▼
统计报告
```

## 三、Config 结构设计

### 3.1 结构定义

Config 为 JSON 数组，每个元素代表一个信源（如交通运输部），内部嵌套 entries（起始页列表）。

```json
[
  {
    "source_name": "交通运输部",
    "base_url": "https://www.mot.gov.cn",
    "configs": {
      "list": {
        "mode": "selectors | script",
        "fields": { ... }
      },
      "pagination": {
        "mode": "selectors | script",
        "fields": { ... }
      },
      "detail": {
        "mode": "selectors | script",
        "fields": { ... }
      }
    },
    "entries": [
      {
        "entry_name": "交通要闻",
        "url": "https://www.mot.gov.cn/xinwen/jiaotongyaowen/index.html"
      },
      {
        "entry_name": "图片新闻",
        "url": "https://www.mot.gov.cn/xinwen/tupianxinwen/index.html",
        "configs": {
          "list": { "mode": "selectors", "fields": { ... } }
        }
      }
    ]
  }
]
```

### 3.2 设计决策

| 决策 | 说明 |
|------|------|
| `mode` 字段 | `"selectors"` 或 `"script"`，互斥，不存在两者都填的情况 |
| `fields` 统一结构 | selectors 模式下 `fields` 是 `{field_name: "css_selector"}`，script 模式下是 `{field_name: "js_code"}`，结构完全对齐 |
| entry 级覆盖 | entry 内只需写差异部分，未定义的字段继承信源级 `configs` |
| `pagination` 为 null | 表示无翻页（如新华社单页加载） |
| 三大功能组独立 | `list` / `pagination` / `detail` 各自独立 mode，互不影响 |

### 3.3 继承机制

```python
def resolve_config(source: dict, entry: dict) -> dict:
    """entry 级覆盖，未定义则 fallback 到 source 级"""
    return {
        "list":       entry.get("configs", {}).get("list")       or source["configs"]["list"],
        "pagination": entry.get("configs", {}).get("pagination") or source["configs"].get("pagination"),
        "detail":     entry.get("configs", {}).get("detail")     or source["configs"]["detail"],
    }
```

### 3.4 mode 选择依据

| 场景 | mode | 理由 |
|------|------|------|
| 标准新闻列表（`ul > li > a`） | selectors | CSS 选择器完全够用 |
| 日期藏在 URL 中（如 `/20260724/`） | script | JS 正则从 href 提取 |
| 翻页用 `onclick="goPage(2)"` | script | JS 提取 onclick 参数 |
| 正文提取需跨元素组合 | script | JS 一次性返回结构化数据 |
| 批量提取 + 数组转换 | script | JS `Array.from().map()` 一行搞定 |

**结论**：CSS 选择器覆盖大部分标准页面，JS 代码块是复杂逻辑的逃生舱。两者结构对齐，crawler 执行层只需一个 mode 分支判断。

### 3.5 selectors 模式 fields 规范

**list.fields**：

| 字段 | 类型 | 说明 |
|------|------|------|
| `container` | CSS | 列表容器，如 `ul.news-list` |
| `item` | CSS | 列表项，如 `li.news-item` |
| `title` | CSS | 标题元素，如 `span.news-title` 或 `a` |
| `date` | CSS | 日期元素，如 `span.news-date` |
| `link` | CSS | 链接元素，如 `a` |
| `link_attr` | string | 链接属性名，固定 `href` |

**pagination.fields**：

| 字段 | 类型 | 说明 |
|------|------|------|
| `next` | CSS | 下一页按钮选择器 |
| `next_text` | string | 按钮文本（用于确认），如 `下一页` |
| `url_pattern` | string | URL 模式（备选），如 `index_{page}.html` |

**detail.fields**：

| 字段 | 类型 | 说明 |
|------|------|------|
| `title` | CSS | 文章标题，如 `h1` |
| `date` | CSS | 发布日期 |
| `content` | CSS | 正文容器，如 `div.article-content` |
| `source` | CSS | 来源信息 |

### 3.6 script 模式 fields 规范

**list.fields**：

| 字段 | 类型 | 说明 |
|------|------|------|
| `items` | JS | 返回 `[{title, date, url}, ...]` 数组的 JS 代码 |

**pagination.fields**：

| 字段 | 类型 | 说明 |
|------|------|------|
| `next_url` | JS | 返回下一页 URL 或 null |
| `has_next` | JS | 返回 boolean |

**detail.fields**：

| 字段 | 类型 | 说明 |
|------|------|------|
| `title` | JS | 返回标题字符串 |
| `date` | JS | 返回日期字符串 |
| `content` | JS | 返回正文文本 |
| `source` | JS | 返回来源字符串 |

## 六、Phase 详细设计

### Phase 1: 信源遍历 & Config 解析

```
对每个 source 的每个 entry:
  1. config_store.load(source.base_url) → 查 DB
  2. resolve_config(source_config, entry) → 合并信源级 + entry 级
  3. Playwright 打开 entry.url
  4. try_extract_items(page, resolved_config.list)
     - mode="selectors" → page.locator() 逐项提取
     - mode="script"    → page.evaluate(fields.items)
  5. 提取结果空或异常？
     - 是 → explorer.explore_list(page) → LLM 分析 DOM → 生成新 config
           → 写回 DB → 重新 try_extract_items()
           → 重试 explore_max_retries 次，仍失败 → 跳过该 entry
     - 否 → 继续 Phase 2
```

### Phase 2: 翻页采集

```
对每个有 config 的 entry:
  1. 当前页 items 提取完成
  2. 日期过滤：检查 items 中的 date
     - 全部 date < start_date → 停止翻页
  3. 翻页：
     - pagination=null → 单页结束
     - pagination.mode="selectors" → click next 按钮 或 goto url_pattern
     - pagination.mode="script" → page.evaluate(fields.next_url) 获取下一页 URL
  4. 终止条件：
     - 当前页所有 items 的 date < start_date
     - 达到 max_pages
     - 翻页返回空页
  5. 合并该 entry 所有 items（仅保留 start_date ≤ date ≤ end_date）
  6. 限速：每次请求间隔 rate_limit_ms（默认 1500ms）
```

### Phase 3: URL 去重

```
所有 sources 的 items 汇总后：
  1. 内部去重：相同 url 只保留一条（dict keyed by url）
  2. DB 去重：
     SELECT link_url FROM documents WHERE link_url IN (...)
     排除已存在的 URL
  3. 输出：待粗筛的 items 列表
```

### Phase 4: 粗筛（LLM 批量）

```
items 按 coarse_batch_size（默认 20）分批：
  1. 构造 prompt：
     - 注入 start_date, end_date
     - 注入用户 preference（如有）到关注范围
     - 注入 items 标题列表（id + title + doc_date + link_url）
  2. 调用 LLM（news-coarse prompt）
     → 返回 {results: [{id, decision: "pass"|"reject"}]}
  3. 保留 pass 的 items
  4. 并发控制：asyncio.Semaphore(3) 限制同时进行的批次
```

### Phase 5: 正文提取

```
对每条粗筛通过的 item:
  1. Playwright 打开 item.url（复用同一浏览器实例）
  2. try_extract_detail(page, resolved_detail_config)
     - mode="selectors" → page.locator(fields.title).inner_text() 等
     - mode="script"    → page.evaluate(fields.title) 等
  3. 提取失败或为空？
     - 是 → explorer.explore_detail(page) → LLM 分析 → 生成 detail config → 重试
     - 否 → 获得 title, content, date, source
  4. 限速：每次请求间隔 rate_limit_ms
```

### Phase 6: 细筛（LLM 逐篇）

```
对每条有正文的 item:
  1. 构造 prompt：
     - 注入 start_date, end_date
     - 注入 title, content, doc_date, link_url
     - 使用 news-fine 提示词
  2. 调用 LLM → 返回：
     - decision: "pass" | "reject"
     - (reject) reject_reason
     - (pass) doc_date, category, digest, insight, score, score_reason
  3. 入库条件：decision="pass" 且 score ≥ 6.0
  4. 并发控制：asyncio.Semaphore(fine_concurrency=3)
```

### Phase 7: 入库 + 统计报告

```
1. 批量 INSERT INTO documents（INSERT IGNORE 跳过 uk_dedup 冲突）
   字段映射：category, title, content, digest, insight,
             link_url, doc_date, website_name, score, score_reason

2. 统计报告（写入 PipelineResult.summary）：
   - 各信源/entry 采集条数
   - URL 去重后条数
   - 粗筛 pass/reject 数
   - 细筛 pass/reject 数
   - 入库条数
   - 各 category 分布
   - 探索 Agent 触发次数 / 成功数 / 失败数
   - 跳过的 entries（及原因）
```

## 七、探索 Agent 设计

### 7.1 定位

探索 Agent 是一个**函数调用模式**（非独立 subagent），在 `explorer.py` 中实现。在 config 缺失或失效时触发。

### 7.2 触发场景

| 场景 | 触发条件 | Agent 模式 |
|------|---------|-----------|
| 列表页 config 缺失 | DB 中无该 base_url 的 config | explore_list |
| 列表页 config 失效 | try_extract_items 返回空 | explore_list（带错误信息） |
| 详情页 config 缺失 | source config 无 detail 部分 | explore_detail |
| 详情页 config 失效 | try_extract_detail 返回空 | explore_detail（带错误信息） |

### 7.3 执行流程

```
输入：Playwright Page 对象（已打开目标页面）

1. page.content() 获取页面 HTML
2. 简化 DOM：去除 script/style/nav/footer，保留主体结构
3. 调用 LLM（explorer prompt）→ 返回 config JSON
4. 验证：用生成的 config 在同一页面上试跑
   - try_extract_items() / try_extract_detail()
   - 成功 → save config to DB, return config
   - 失败 → 将错误信息反馈给 LLM，重试
5. 最大重试 explore_max_retries 次（默认 3）
6. 仍失败 → 返回 None，由调用方跳过该 entry
```

### 7.4 探索 Agent 提示词（列表页）

```
## 角色
你是一个网页结构分析专家。你的任务是分析一个新闻列表页的 DOM 结构，
生成用于自动化采集的配置。

## 输入
1. 页面的简化 DOM 快照（已去除 script/style/nav/footer）
2. 页面 URL：{url}
3. 信源名称：{source_name}

## 任务
分析 DOM 结构，输出配置 JSON，包含三个部分：

### list（列表提取）
- 识别新闻列表的容器和列表项
- 每项需提取：标题(title)、链接(link)、日期(date)
- 优先使用 CSS 选择器（mode="selectors"）
- 如果选择器无法完成（如日期藏在 URL 中、需要复杂逻辑），使用 JS 代码块（mode="script"）

### pagination（翻页）
- 识别翻页机制：下一页按钮 / URL 模式 / JS 函数 / 无翻页
- 无翻页时输出 null

### detail（详情页，推断）
- 基于常见政府网站结构推断详情页的标题、正文、日期、来源选择器

## 输出格式
严格输出 JSON，不输出解释文字。

{config_json_schema}

## 约束
- 选择器必须能在当前页面匹配到 ≥1 个元素
- JS 代码必须是可直接 page.evaluate() 的纯函数体
- 日期格式统一为 YYYY-MM-DD
```

### 7.5 探索 Agent 提示词（详情页）

```
## 角色
你是一个网页正文提取专家。

## 输入
1. 详情页的 DOM 快照
2. 页面 URL：{url}

## 任务
从 DOM 中识别并输出以下配置：
- title: 文章标题（通常是 h1 或最大的标题元素）
- content: 正文内容（最长的文本块容器，排除导航/广告/评论）
- date: 发布日期（YYYY-MM-DD）
- source: 来源信息

## 输出格式
严格输出 JSON，不输出解释文字。

{detail_config_json_schema}

## 约束
- 选择器或 JS 代码必须能在当前页面提取到非空内容
- 正文容器应包含 ≥50 字的连续文本
```

### 7.6 修复模式提示词补充

当 config 验证失败时，追加以下信息：

```
## 上次尝试失败
你生成的配置提取结果为空。
错误信息：{error_message}
提取到的 items 数量：{count}

请重新分析 DOM 结构，修正选择器或 JS 代码。
```

## 八、数据库设计

### 8.1 表 1：`news_source_configs`（信源配置，LLM 自管理）

```sql
CREATE TABLE news_source_configs (
  id              BIGINT AUTO_INCREMENT PRIMARY KEY,
  source_name     VARCHAR(255)   NOT NULL COMMENT '信源名称（如：交通运输部）',
  base_url        VARCHAR(1000)  NOT NULL COMMENT '信源根域名',
  config_json     JSON           NOT NULL COMMENT '完整配置（source级configs + entries级覆盖）',
  last_verified   DATETIME(6)    DEFAULT NULL COMMENT '最近一次成功采集时间',
  explore_count   INT            NOT NULL DEFAULT 0 COMMENT '探索Agent累计触发次数',
  created_at      DATETIME(6)   NOT NULL DEFAULT CURRENT_TIMESTAMP(6),
  updated_at      DATETIME(6)   NOT NULL DEFAULT CURRENT_TIMESTAMP(6) ON UPDATE CURRENT_TIMESTAMP(6),
  UNIQUE INDEX uk_base_url (base_url(500))
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='资讯采集信源配置（LLM自管理）';
```

`config_json` 存储完整的信源配置（含 `configs` + `entries`），与 pipeline 用户输入的 `sources` 数组中的单个信源结构一致。

### 8.2 表 2：`documents`（素材库）

沿用 RPA 交付包的 `documents` 表设计：

```sql
CREATE TABLE documents (
  id            BIGINT         NOT NULL AUTO_INCREMENT PRIMARY KEY COMMENT '自增主键',
  category      VARCHAR(50)    NOT NULL COMMENT '13个分类之一',
  title         VARCHAR(500)   NOT NULL COMMENT '原始标题',
  content       LONGTEXT       NOT NULL COMMENT '正文全文',
```

## 九、限速与反爬策略

### 9.1 问题背景

实测发现：交通运输部官网（mot.gov.cn）在约 10 分钟内接收 20+ 次 Playwright 请求后，返回 403 封禁 IP。该封禁与 headless 模式无关（headless=True/False 均被封），确认为 IP 级限频。

### 9.2 限速策略

| 策略 | 具体措施 | 配置项 |
|------|---------|--------|
| **请求间隔** | 同域名请求间隔 ≥ 2 秒 | `rate_limit_ms: 2000` |
| **信源切换延迟** | 不同信源间切换时加 5 秒延迟 | `source_switch_delay_ms: 5000` |
| **每日配额** | 每个信源每日请求上限 | `daily_quota_per_source: 200` |
| **Session 复用** | 先访问首页拿 cookie，再访问子页面 | crawler 内置 |

### 9.3 403 退避策略

```
遇到 403:
  1. 立即停止该信源的所有请求
  2. 记录 crawl_log: status="403_blocked"
  3. 指数退避：
     - 第 1 次：等待 5 分钟后重试
     - 第 2 次：等待 10 分钟
     - 第 3 次：等待 30 分钟
     - 超过 3 次：跳过该信源，记录到统计报告
  4. 退避期间继续处理其他信源
```

### 9.4 断点续采

```
每次翻页成功后，写入 crawl_log（page_number + items_found）
pipeline 重启时：
  1. 查询 crawl_log 获取已完成的 page_number
  2. 从 max(page_number) + 1 继续
  3. 已采集的 items 通过 DB 去重自动过滤
```

## 十、错误处理

| 阶段 | 错误类型 | 处理方式 |
|------|---------|---------|
| 页面加载 | 超时（30s） | 重试 1 次 → 跳过该 entry，记录 crawl_log |
| 页面加载 | 403/封禁 | 指数退避（5/10/30min）→ 仍失败则跳过整个信源 |
| Config 缺失 | 无预存 config | 触发探索 Agent → 生成 → 验证 → 存 DB |
| Config 失效 | 提取结果为空 | 触发探索 Agent 修复 → 验证 → 更新 DB config |
| 探索 Agent | 重试 N 次仍失败 | 跳过该 entry，记录 error，继续下一个 |
| 粗筛 | LLM 调用失败 | 重试 2 次 → 跳过该批次，记录 error |
| 正文提取 | 页面 403 | 跳过该条，记录 crawl_log |
| 正文提取 | 内容为空 | 触发探索 Agent detail 模式 → 重试 |
| 细筛 | LLM 调用失败 | 重试 2 次 → 跳过该条 |
| 入库 | uk_dedup 冲突 | INSERT IGNORE，静默跳过 |

## 十一、入库阈值

| 条件 | 值 | 说明 |
|------|---|------|
| `decision` | `"pass"` | 细筛 GATE 通过（日期在周期内 + 与港航相关 + 非固定数据类） |
| `score` | ≥ 6.0 | news-fine 四维加权评分（0~10 分制） |

评分校准（沿用 news-fine 提示词）：
- 8.0+：栏目内最优质少数素材
- 6.0~7.9：合格素材正常区间
- < 6.0：入刊价值低

6.0 作为入库线 = 仅保留合格及以上素材。后续 TopK 选优时由 score 排序自然淘汰低分素材。
